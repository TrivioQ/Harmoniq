# Multi-Tenancy & Tenant Admin — Gap Analysis

> **Date:** 2026-10-11 · **Scope:** tenant model (Instance → Organization → Workspace), tenant isolation, tenant administration (org dashboard and API), instance (operator) administration, and the enterprise features they need.
> **Basis:** code on `main` at `604a1a3`: `apps/registry`, `apps/web`, `packages/db`, `packages/core`, plus `docs/requirements.md`.
> **Follow-up:** requirements in [requirements.md §19](./requirements.md), tasks in [implementation-plan.md Phase 9](./implementation-plan.md), design and status in [features/tenant-administration.md](./features/tenant-administration.md).

## 1. Summary

The foundation is strong. Workspace isolation is enforced in Postgres (RLS on a non-owner role), not only by application filters. SSO and SCIM work at both the workspace and the org level. Audit logs exist at all three levels and export to CSV or JSON Lines. Org API keys support IaC, and the approval, freeze and ownership controls go further than most competing products.

The **tenant admin experience is thin**, though, and several **lifecycle and integrity paths are incomplete**. An enterprise buyer's first two weeks (onboarding people, offboarding people, proving usage, controlling policy across teams, and leaving cleanly) all hit a gap:

| Area                                    | Maturity | Headline gap                                                                                                  |
| --------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------- |
| Data isolation (DB)                     | ●●●●○    | Org-level tables and cross-tenant reads rely on application checks only; default role password in a migration |
| Tenant lifecycle (create → delete)      | ●●○○○    | Deletion destroys audit history and leaves objects and manifests in storage; ownerless workspaces             |
| People lifecycle (invite → offboard)    | ●●○○○    | No invitation emails; removing an org member leaves their workspace access and keys                           |
| Tenant admin dashboard (org)            | ●●○○○    | No org settings, policies, usage, people view or key management parity                                        |
| Policy and governance across workspaces | ●○○○○    | No org-wide policies (ORG-08 approval defaults not built)                                                     |
| Plans, quotas, usage and billing        | ●○○○○    | Feature flags only; no quotas, metering or storage usage (INST-09)                                            |
| Identity security                       | ●●●○○    | Unverified SSO domains (cross-tenant discovery hijack); no MFA or session policy                              |
| System (instance) administration        | ●●○○○    | Admins can lock everyone out; counts-only dashboard; no admin roles, automation, key rotation (§8)            |

The **P0** items in §3 are correctness or security defects and should be fixed before any enterprise sale. Most of §4 is product work for the tenant admin dashboard. §6 gives an ordered roadmap.

## 2. Current tenant model (as built)

```text
Instance (InstanceAdmin, InstanceConfig, InstanceAuditEvent)
└── Organization  [optional]  roles: org_admin | org_member     (system tables, no RLS)
    │   SSO (OIDC/SAML), SCIM, group→workspace rules, OrgApiKey, OrganizationAuditEvent, plan
    └── Workspace  ← the RLS tenant (app.current_workspace_id)   roles: owner | admin | developer | viewer
            HostApps → Environments → RemoteModules → ModuleVersions
            ApiKeys, Webhooks, AlertRules, ApprovalPolicies, BYOB storage, SSO/SCIM, AuditEvent, plan
```

- **Access resolution:** `requireWorkspace` in [authenticate.ts](../apps/registry/src/plugins/authenticate.ts#L328-L434) gives org admins an implicit `admin` role in every workspace of their org. Org keys bind to the requested workspace for each request.
- **Effective plan:** the higher of the workspace plan and the org plan ([plans.ts](../apps/registry/src/services/plans.ts#L42-L59)).
- **Isolation:** `withTenant` runs a `set_config` local to the transaction ([packages/db/src/index.ts](../packages/db/src/index.ts#L37-L49)). Org routes, admin routes and background jobs use `systemDb`, the owner role, which bypasses RLS.

## 3. P0: defects and risks to fix first

| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0-1 | **Ownerless workspaces are stuck forever.** Workspaces created with an org key (Terraform, IaC-01) have no owner. Org admins get only `admin`, and only owners can grant `owner`. Nobody can ever override a freeze, bypass an approval or share a module org-wide in those workspaces.                                                                       | [workspaces.ts:18-33](../apps/registry/src/services/workspaces.ts#L18-L33), [access.ts:241-244](../apps/registry/src/routes/access.ts#L241-L244), [authenticate.ts:411](../apps/registry/src/plugins/authenticate.ts#L411); owner-gated routes in `hostApps.ts:592`, `approvals.ts:299`, `orgs.ts:735` | Let org admins assign `owner` in org workspaces, or treat `org_admin` as `owner` for ownerless workspaces. Add an `owner` (email) field to org workspace creation and to the Terraform resource.                                         |
| P0-2 | **Deleting a workspace erases its audit trail.** `AuditEvent`, `ScimAuditEvent` and approvals cascade on `Workspace` delete. Only a one-line instance or org event survives. That breaks compliance retention (SOC 2, ISO 27001).                                                                                                                             | [schema.prisma:361](../packages/db/prisma/schema.prisma#L361), [workspaces.ts:83-101](../apps/registry/src/services/workspaces.ts#L83-L101)                                                                                                                                                            | Soft-delete workspaces (`deletedAt`, a restore window of e.g. 30 days, then a purge job). Archive the audit rows (detach the FK, or copy them to an archive table or object storage) before the hard delete.                             |
| P0-3 | **Deleting a workspace leaves tenant data in storage.** Published manifest and import-map copies (CDN) and BYOB bundles are not removed. Versions cascade-delete, so their `storagePath` is lost and the hard-delete GC can't purge them. Deleted tenants keep serving manifests from the CDN.                                                                | `deleteWorkspace` vs. the cleanup in the ephemeral-env path ([gc.ts:234-243](../apps/registry/src/jobs/gc.ts#L234-L243))                                                                                                                                                                               | Collect environment publish paths and version `storagePath`s before the delete and enqueue a purge job (instance storage plus the BYOB bucket). Run the same job on the suspension hard-delete path.                                     |
| P0-4 | **SSO trusted domains are unverified and first-match-wins across tenants.** Any workspace or org admin can list `acme.com` (or `gmail.com`). `/api/auth/sso/discover` then routes every user of that domain to the first matching IdP, which can be an attacker-controlled one (phishing, login hijack). The lookup also scans every SSO config on each call. | [auth.ts:119-165](../apps/registry/src/routes/auth.ts#L119-L165)                                                                                                                                                                                                                                       | Domain verification (DNS TXT challenge, `VerifiedDomain` table with a unique domain), discovery only on verified domains, instance-admin override. Index the lookup by domain.                                                           |
| P0-5 | **Removing an org member doesn't offboard them.** Only the `OrganizationMember` row is deleted. Their workspace memberships (including `orgProvisioned` ones), workspace API keys and sessions stay. SCIM deprovisioning does all of this, but the manual path doesn't.                                                                                       | [orgs.ts:394-411](../apps/registry/src/routes/orgs.ts#L394-L411)                                                                                                                                                                                                                                       | Reuse the SCIM deprovisioning routine, with an "also remove from N workspaces / revoke M keys" confirmation.                                                                                                                             |
| P0-6 | **A migration can create the app role with a placeholder password.** The RLS migration creates `harmoniq_app` with the password `'password'` if the role doesn't exist. `self-hosting.md` tells operators to run `scripts/bootstrap-db.ts` (or `docker/init.sql`) first, but a database migrated without that step gets a known credential.                   | [20260913182039_rls/migration.sql:4](../packages/db/prisma/migrations/20260913182039_rls/migration.sql#L4), [self-hosting.md](./self-hosting.md)                                                                                                                                                       | Fail the migration when the role is missing, with the bootstrap instruction (MT-11).                                                                                                                                                     |
| P0-7 | **No defense in depth for org-scoped data.** `Organization*`, `OrgApiKey`, org-scoped `ScimUser`/`ScimGroup`, and all cross-workspace reads (org home, catalog, org audit) go through `systemDb`, which bypasses RLS. A missing `organizationId` filter leaks across orgs. `orgs.ts` alone has 46 `systemDb` calls.                                           | [orgs.ts](../apps/registry/src/routes/orgs.ts), [orgShared.ts](../apps/registry/src/services/orgShared.ts)                                                                                                                                                                                             | Add an `app.current_org_id` setting plus RLS policies on org tables and an org-scoped `withOrg()` helper. Add a lint rule or review checklist for `systemDb` in route handlers, and a cross-org isolation test suite like `rls.test.ts`. |

### 4.9 Scale and performance of tenant views

- The org home, catalog and members endpoints are unpaginated and load every workspace, module and active version (`orgs.ts:214-275, 700-730`). Large orgs (100+ workspaces, 1,000+ modules) will slow down. Add pagination and pre-aggregated rollups. **P2**
- The org audit merges two streams in memory (`take: limit+1` each). This is fine, but each filter by actor needs a user lookup by email; add one. **P3**
- Every authenticated workspace request runs `organizationMember.count` for the org-admin check. Cache it along with the plan cache. **P3**

## 8. System (instance) administration

The instance admin has a setup wizard, health checks, workspace, user and org lists, admin grants, four runtime settings (storage, email, sign-in, branding) and an append-only audit log (`routes/admin.ts`, `apps/web/src/app/[locale]/admin`). That covers first boot and basic tenant moderation. It doesn't yet cover day-2 operation of a production instance: knowing what needs attention, running jobs, rotating secrets, recovering from mistakes, delegating safely and automating.
